# M9：签名、升级与 GitHub Releases 发布

文档版本：1.0 · 目标：1.0.0-harmony · [返回索引](README.md)

## 1. 发布范围

本期沿用项目约定：分发 HarmonyOS HAP 到 GitHub Releases，不新增 AppGallery 上架流程。发布目标是接收者按文档能实际安装和升级，不能只证明开发机能通过 hdc 安装。

下述命令沿用现有项目工具，执行前通过本地帮助及版本核对参数。签名凭据、服务端权限与设备限制需实测；计划文档不保证自动签名命令必然产生通用分发产物。

## 2. 提前验证：M4 后执行一次

1. 记录 devecocli、SDK、构建工具版本和当前签名方式。
2. 核对 `devecocli auth login` 与 `devecocli signature generate --product default` 的实际作用及证书类型。
3. 构建测试产物，在另一台目标设备或干净环境按计划分发方式安装。
4. 明确是否绑定设备、需要何种证书/描述文件、接收者需执行什么步骤。
5. 若渠道受限，修正文档与分发方式后再继续；不能等 M9 才发现公开 HAP 不可安装。

证书、私钥、密码与本地签名路径不提交仓库。自动流程不适用时记录 DevEco Studio 操作步骤，但仍验证产物安装性。

## 3. 发布候选准备

1. 核对 M4–M8 完成证据与已接受差异，移除占位入口或明确标记不可用功能。
2. 确认最终 bundleName 为 `com.reqir.misakaquiz`，应用名、图标、权限与版本正确。
3. 版本改为 `1.0.0-harmony`，versionCode 大于已分发的所有版本。
4. 更新 CHANGELOG、移植进度、README 特性矩阵、构建/签名/安装步骤和下载入口。
5. 在可复现的源码状态构建；工作区存在无关改动时逐项排除，记录确切提交。

## 4. 构建与产物检查

在 `apps/harmony` 中执行已核对参数的 `devecocli build --build-mode release`。

- 从实际构建输出定位 HAP，不猜测固定路径。
- 检查实际签名、版本、包名、架构/API 要求、图标。
- 使用 PowerShell `Get-FileHash -Algorithm SHA256 -LiteralPath <产物路径>` 生成哈希。
- 最终安装测试必须使用待上传的同一文件，测试后不得无记录重打包。
- 保留产物文件名、字节大小、SHA256、源提交、构建工具版本和测试设备。

## 5. 安装与升级验收

| 路径 | 必须验证 |
| --- | --- |
| 干净安装 | 首次启动、空态、C1 导入、练习/考试 |
| 0.4.1 或最早公开测试版升级 | 旧题库、中文、图片、默认字段处理 |
| 最近阶段版升级 | 错题排期、收藏、记录、顺序进度、设置、AI 缓存 |
| 升级中数据读取异常 | 保留旧文件、恢复提示，不静默清空 |
| 外部分发安装 | 按 README 完成，证书与设备限制说明真实 |

升级前后用代表性数据清单核对，不能仅看启动成功。若旧安装无法被新签名覆盖，必须在发布前解决或明确备份迁移路径。

## 6. 自动化与发布流程

先检查仓库 `create-releases.cmd` 与现有 CI 是否可复用。只有现有入口无法覆盖鸿蒙时才新增 `scripts/release-harmony.cmd`。

脚本流程：环境预检 → 测试 → Release 构建 → 产物定位与核验 → 哈希 → 输出待发布说明。构建失败立即停止；不能发布残留旧 HAP。上传步骤应与准备步骤区分，并按当前任务授权执行。

人工发布清单：

- [ ] 最终提交与 release tag 一致，例如 harmony-v1.0.0。
- [ ] Release 说明包含版本、安装条件、特性、已知差异、升级/恢复说明。
- [ ] 上传核验过的 HAP 与 SHA256 文件，不含证书或私人数据。
- [ ] 上传后核对下载文件哈希与本地相同，README 链接可达。
- [ ] 保存发布地址和对应提交到进度记录。

## 7. 回退与问题处理

保留上一稳定产物与备份说明。数据格式已升级时，安装旧包未必能恢复数据；不承诺直接降级。优先使用已验证兼容备份恢复，或发布更高 versionCode 的修复版。

发布阻断问题包括数据丢失、计时/判分错误、不可安装、备份损坏、Key 泄露。遇到问题停止发布，记录失败步骤与修复后复验；不要仅修改发布说明掩盖阻断缺陷。
