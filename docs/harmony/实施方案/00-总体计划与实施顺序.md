## 3. 每项任务的实施流程

1. 阅读 Android 对应函数、全部调用者、模型与序列化，形成输入、输出、副作用清单。
2. 搜索鸿蒙已有实现，优先补齐现有 Repository/Core/Models，不重复创建平行逻辑。
3. 明确正常、空数据、重复操作、失败路径，以及 Android 与鸿蒙差异。
4. 将可测逻辑留在 ArkTS 兼容 `.ts` 中；平台文件、网络、生命周期适配留在 `.ets`。
5. 先实现共享逻辑及最小可运行自检，再接 Repository 和 UI。
6. 跑受影响检查、ArkTS 编译、设备场景；通过后写证据，再收尾文档与版本。

不引入通用任务框架、数据库迁移框架或新 UI 层；只有现有实现无法满足明确需求时才扩大改动。

## 4. 版本与变更管理

- 实际版本改动遵守 AGENTS.md：递增版本号，记录 Markdown 变更。
- M4 计划 versionCode `6`；后续以实际当前值递增，不因阶段编号预写固定值。
- 每个完成里程碑同步 `AppScope/app.json5`、根 CHANGELOG 的 HarmonyOS 段、移植进度。
- 小修补如独立交付，也必须递增版本；不能沿用旧 versionCode 发布新包。
- 提交前检查 `git status` 与 diff，只纳入本任务文件；现有 `.reasonix`、`reasonix.toml` 等改动不自动包含。
- 原清单的阶段提交、分支约定属于计划要求，不扩写成 AGENTS.md 的原文要求；提交、打标签与发布按实际任务授权执行。
- 清理临时文件只处理确认由当前任务产生且不再需要的路径，不执行未经核对的批量递归删除。

## 5. 优先级与范围控制

P0：数据丢失、错误判分、考试计时、交卷重复、导入破坏旧数据、AI 写错题库。

P1：动态布局、作用域、数据互通、错误反馈、旧数据升级、大字号可操作。

P2：可跳过开屏、吉祥物、公式排版增强、非必要动效。

默认保留原计划的完整功能范围。若希望提前发布，只有明确记录并接受差异后，才能将 M8b 或 P2 项移到后续版本；不能在验收时静默省略。

## 6. 完成定义

一个阶段完成必须同时满足：代码实现、共享逻辑自检、实际构建、设备闭环、失败路径、版本文档、已知差异记录。仅“Node 全绿”或“页面能打开”均不等于完成。
